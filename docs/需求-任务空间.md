# 需求：聊天空间与任务空间分开

- 整理：2026-11-18（多轮讨论后定稿）
- 状态：已完成（2026-11-18），实现情况见文末
- 更新：2026-11-19 新增「规划前澄清」；2026-11-19 协调者和后端已完成，界面和记忆库还没接（见该节「实现情况」）

## 一句话

空间分成两类：**聊天空间**用来自由讨论，**任务空间**用来围绕一个目标让多个 AI 分工干活。在聊天空间里讨论出方案后，可以直接转到一个新的任务空间开工。

## 为什么改

现在一个空间里既有聊天也有任务协作，带来三个问题：

- 任务规划、写总结、"依次直接改"执行时，聊天被锁住，不能用；
- 任务一开始执行，就没有渠道再给它补充要求，只能停掉子任务再退回；
- 任务看不到聊天里讨论出的方案，开任务时要把目标重新写一遍。

分开以后，一个空间只做一件事，锁聊天的规则整个去掉；任务空间的输入框就是"和协调者说话"。

## 两类空间

| | 聊天空间 | 任务空间 |
| --- | --- | --- |
| 做什么 | 自由讨论，可以改共享文件 | 完成一个任务（定义见下） |
| 输入框发给谁 | 所有成员，按现在的轮流和 @ 规则 | 只发给协调者 |
| 成员 | 新建时选 | 新建时**重新选**，并指定协调者 |
| 侧栏 | 和任务空间混在一起，**用图标区分** | 同左 |

## 「一个任务」的定义

一个任务空间只做一个任务：**一个目标，加上为它服务、可以不断修改的一份计划，从开工持续到你宣布结束。**

- **起点**：从聊天空间转来的方案，或新建时直接写的目标，就是这个任务的总目标；
- **过程**：规划 → 执行 → 审查 → 总结。中途为同一个目标补充要求、改做法、调整范围，都还是这个任务；
- **做完以后**：协调者写完总结，任务不立刻关闭，你还可以接着提要求，协调者追加子任务；
- **终点**：你点「结束任务」（Git 项目一般在合并之后）。结束后任务空间只读，留作记录；可以点「再开一个类似的任务」，新建一个任务空间，成员和设置照搬，目标重新写；
- **边界**：新消息和总目标无关时，协调者不硬塞进计划，而是提示你新开一个任务空间。判断标准是"能不能写进同一份总结"。

## 建任务空间

两个入口：

1. **侧栏直接新建**：选「任务空间」，写目标、选成员和协调者、选共享文件夹，和现在新建空间差不多；
2. **从聊天空间的方案转过去**：转到一个新的任务空间，协调者可以在转的时候就选好。方案有两种选法：
   - **手动挑选**：在消息上选「转到任务空间」，可以多选，挑哪几条带哪几条；
   - **让 AI 整理**：选一段讨论，由一个成员提炼成方案，你看过、改过再确认。

新建时还要选：

- **计划确认方式**：协调者定好计划（包括中途改过的计划）后，是**自动开始执行**，还是**等你确认**。建好后在任务空间的设置里随时能改。（合并 [待办](待办.md) 第 1 项「计划自动确认」）
- 沿用现有的选项：其他成员是否审阅计划、子任务做完是否自动通过、Git 项目最多同时做几个。

确认后直接进入规划，不用再填一遍目标。

## 规划前澄清（2026-11-19 新增；协调者和后端已完成，界面还没做）

目标说得含糊时，协调者不硬猜；但也不能为此把「一句话做成一件事」变成一轮问答。只问猜错了代价大的事，其余的列成假设，交给后面的「中途的新消息」兜底。

- **由协调者判断要不要问**：目标够清楚就直接规划。只有不同的理解会做出明显不同的结果时才问，例如「做个登录页」是只要账号密码，还是要短信验证码。
- **一次问完，最多三个，每个都带默认答案**，例如「登录方式？默认：账号密码」。你可以只回答其中几个，没回答的按默认；或者直接点「按默认开始」。
- **没回答时**：
  - 计划确认方式是「自动开始执行」的：等 10 分钟没回答就按默认开始，计划的假设里注明「按默认处理」；
  - 计划确认方式是「等你确认」的：一直等。
- **计划里的假设**：协调者自己拿主意的地方（包括按默认处理的问题），在计划开头列成几条假设。确认计划时一眼能看到；自动开始的，发现不对就直接说，按「中途的新消息」处理。
- **记进记忆库**：澄清时的回答和假设记成决定（见 [需求-记忆库](需求-记忆库.md)），所有工作者看到的是同一份。
- **从聊天空间转来的任务不问**：方案已经讨论过了；要先多聊几句的，本来就该在聊天空间里聊完再转过来。

几道保护合起来：

| 时机 | 怎么处理 |
| --- | --- |
| 规划前 | 协调者判断需要时，最多问三个问题，每个带默认答案 |
| 规划时 | 自己拿主意的地方列成「假设」 |
| 进行中 | 发现不对直接说，协调者判断是补充还是改计划（见下一节，已完成） |
| 全程 | 回答和决定记进记忆库 |

- **定时建出来的任务空间也不问**（2026-11-19 定）：没人在场，直接按默认答案开始，列进假设。

### 模块与接口（2026-11-19，已按此实现）

这一批只做协调者和后端；问题卡片的界面、计划开头的假设怎么显示，等前端框架合进来以后再做。「记进记忆库」等记忆库做好再接。

| 模块 | 做什么 | 对外接口 |
| --- | --- | --- |
| `src/task-prompts.mjs` | 规划提示里加澄清的规则；规划结果里加假设 | `parseClarify(text) → { questions: [{ id, text, default }] } \| null`（超过三个只取前三个）；计划解析多一个 `assumptions: string[]` |
| `src/taskrun.mjs` | 第一次规划前先让协调者判断要不要问；新状态 `clarifying`；回答后带着答案规划；自动开始的等 10 分钟按默认开始，软件重开后接着算剩下的时间 | `run.data.clarify = { questions, answers, askedAt, deadline? }`；`answerClarify(answers)`（只回答几个也行，没回答的按默认）；`useDefaults()`；建任务时的选项 `clarify: false` 表示不问（从聊天空间转来、定时建的） |
| `src/space.mjs`（只动 `runAction` 和建任务的那一处） | 接两个动作；建任务时决定问不问 | `clarify-answer`（`{ answers }`）、`clarify-defaults`；新建参数 `clarify`，从聊天空间转来的（有 `source`）一律不问 |

- 「要不要问」由协调者在第一次规划的那次调用里一起判断，不多花一次调用：要么给出问题，要么直接给计划。
- 只有第一次规划会问；你中途发的新消息、退回重新规划都不问。
- 测试（模拟 AI）：清楚的目标直接规划；含糊的目标问问题；只回答一部分；按默认开始；自动开始的 10 分钟超时（假时钟）；等你确认的一直等；`clarify: false` 不问；假设出现在计划里。

### 实现情况（2026-11-19）

协调者和后端已完成，`npm run verify` 通过（新增 `test/clarify.test.mjs`，13 个测试，全部用模拟 AI 和假时钟）。只在 Windows 上跑过测试；没有用真实账号试过协调者「该不该问」的判断，也没有在软件界面里走过（问题卡片还没做）。

- **接口和上表一致**，多出的几处：
  - `task-prompts.mjs` 新增 `parsePlan(text) → { tasks, assumptions } | null`；原来的 `extractPlan` 保留，返回 `parsePlan(text)?.tasks`。`plannerSystem` 多一个选项 `{ clarify }`，只在能问的那次附上澄清规则（`tasks.clarify`）。
  - `taskrun.mjs` 导出 `CLARIFY_WAIT`（10 分钟）和可替换的 `clock`（测试用假时钟）。建任务的选项存成 `run.data.clarifyFirst`；问完后 `run.data.clarify` 还会多 `resolvedAt`、`defaulted`（按默认处理的问题 id）、超时的 `timedOut`。计划的假设存在 `run.data.assumptions`。
- **只在第一次规划时问**：条件是允许问、还没问过、还没有计划、没有意见（中途新消息、退回重新规划、规划失败后再规划都不问）。协调者回复里有计划就按计划走；没有计划才看是不是问题，问了就进 `clarifying`。
- **假设**：按默认处理的问题由软件生成，排在最前面（「登录方式？：按默认处理（账号密码）」），协调者只写自己拿主意的地方。重新规划时协调者没给假设就沿用之前的。用户的回答和假设会作为「已经定下的」交给每个子任务的负责人和处理中途消息的协调者；先商量时审阅的成员也能看到问答。
- **计时**：自动开始的从提问时算 10 分钟；软件重开后按剩下的时间继续，已经过了就马上按默认开始。等回答期间在设置里把确认方式改成自动开始，也从最初提问的时间算；改成等你确认就不再计时。结束任务、删除空间会清掉计时。
- **等回答期间**：在输入框发的消息先排队，计划出来后再交给协调者，按「中途的新消息」处理。`clarifying` 在侧栏算「等你处理」（`runNeedsUser`）。
- **动作**：`clarify-answer`（`{ answers: { Q1: '…' } }`，也接受 `[{ id, text }]`）、`clarify-defaults`。建任务的 `clarify` 选项：有 `source` 的（从聊天空间转来）一律不问。
- **演示模式**：目标里含「含糊」（英文 `vague`）时，演示协调者会问两个带默认答案的问题；计划里带一条演示假设。
- **还没做**：
  - 提醒：`app-server.mjs` 的 `taskAlerts` 还没有 `clarifying`，所以协调者提问时不会弹系统通知（侧栏的「等你处理」是有的）。等定时任务那边改完 `app-server.mjs` 后加一行：`if (r.status === 'clarifying') out.set('clarify', tr('协调者有几个问题等你回答'));`（文字的英文已经加好）。
  - 前端：问题卡片、计划开头显示假设、`clarifying` 状态的文字。
  - 记进记忆库。

## 中途的新消息

不管哪个 AI 在干活，你在任务空间发的消息都先交给**协调者**：

1. 协调者拿到你的新消息、当前计划、各子任务状态，以及正在进行的子任务已经做了什么；
2. 判断新要求和正在做的有没有冲突：
   - **没有冲突**：记为补充说明，分给相关子任务。还没开始的写进说明，正在做的在下一次做时带上；
   - **有冲突**：停掉受影响的子任务，修改计划：改子任务、增删子任务、换负责人、调整依赖。被停掉的子任务已经做了一半的改动留着还是丢掉，由协调者决定；
3. 改过的计划按新建时选的「计划确认方式」处理：自动开始，或等你确认；
4. 协调者的判断显示成一张卡片：停了什么、改了什么、为什么。

## 共享文件夹

任务空间和某个聊天空间用同一个文件夹时：

- **Git 项目**：子任务都在独立副本里做，审查通过才合并，聊天空间照常使用，互不影响；
- **不是 Git 项目**（依次直接改）：任务执行期间，用同一个文件夹的聊天空间**只能读、不能改文件**，聊天照常进行；执行结束后恢复。
  - 聊天成员发言时被告知"文件暂时只读"；你在文件面板里也不能编辑、撤销；
  - 界面提示：只在文件面板标题旁加一个小锁图标，鼠标停上去显示原因，不加横幅或其他文字。

## 两边的关系

- 聊天空间 → 任务空间：只转选出的方案，多余的消息不带过去；
- 任务空间 → 聊天空间：任务结束时问你要不要把总结发回原来的聊天空间（只有从聊天空间转来的任务才问）；
- 除此之外两边不互通。

## 现有的空间

不做兼容：升级后，现有的空间（里面既有聊天也有任务）**全部删掉**。

- 软件自己创建的共享文件夹随空间一起删除；你自己选的文件夹和里面的文件不动；
- 发布说明里要写清楚，提醒用户升级前把需要的聊天导出（空间里已有「导出」）。

## 实现情况（2026-11-18）

以上内容都已完成，用演示模式走通了全流程，`npm run verify` 通过（新增 `test/taskspace.test.mjs`）。还没有用真实账号跑过协调者的判断。

- **数据**：空间多了 `kind`（`chat` / `task`）。任务空间只有一个任务（`runs[0]`），对话记录里多了协调者的回复（带 `decision`）和总结（`kind: 'summary'`）；发回聊天空间的总结是 `kind: 'task'`，聊天成员看得到。
- **协调者的判断**：协调者先用一两段话回复你，最后附一段 JSON（`answer` / `note` / `change` / `unrelated`），软件按它改计划。已通过的子任务不能改，协调者没写进新计划的也照样留着；正在做、但被删掉或改了说明 / 负责人的子任务，协调者没点名时默认停下并留着改动。丢掉改动：依次直接改的按这一次的改动记录撤销；Git 项目把副本退回这一次开始前。
- **等你确认**：执行中改过计划且选了「等我确认」时，已经在做的子任务照常做完，新的子任务等你确认后才派。
- **做完以后接着提要求**：协调者追加子任务后，任务回到执行中，做完再写一次总结（每次一张总结卡片）。Git 项目已经合并过的，会从你当前的分支重新开一个集成分支。
- **结束任务**：正在做的先停下；通过但没合并的改动留在 `agenda-<编号>` 分支上。
- **文件夹只读**：按完全相同的路径判断（任务空间用的是聊天空间的子文件夹时不算）。聊天成员被告知只读，并且这一轮按“只读”权限运行。
- **升级**：启动时删掉没有 `kind` 的旧空间，删除方式和手动删除空间相同；界面提示一次删了几个。
- **界面**：参考 OpenMausBot 的对话流 + 卡片；按 unslop 的方向小修了全局：按钮里的「＋」和提示里的「⚠」换成线条图标、去掉正在发言头像的循环光圈和绿点外发光、零碎间距回到 4px 网格；珊瑚色（logo 里那个）只用在“等你处理”上。
- **没做**：聊天空间里原来的「任务协作」页和它的提示条都去掉了；导入对话在任务空间里也能用，但从聊天空间转过去时不会带上聊天空间导入的对话。
