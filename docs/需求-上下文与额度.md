# 需求：上下文管理、监视器与额度

- 整理：2026-11-18；更新：2026-11-19，加入上下文管理和自动交接；2026-11-20，和 Codex 讨论后加入按编号回查原文、交接说明先写试过什么、面板记下送进去的条目编号
- 起因：
  - Agenda 里每个成员看到的东西都不一样（任务空间的工作者只看自己的子任务，按主题交接后只看简报，导入的长对话会压成摘要，较早的长回复只留开头和结尾，Claude Code、Codex 自己也会压缩会话），用户常遇到「它怎么不知道 X」却没法查。几个 AI 一起跑又很费额度，现在用完了才报错。额度显示参考了 [Orca](https://github.com/stablyai/orca)。
  - 一个空间要能一直用下去，不靠用户开新空间、写交接文档（见 [需求说明](需求说明.md) 的「产品重点」）。前情提要、自动交接参考了 [OpenMausBot](https://github.com/milind-soni/OpenMausBot) 的上下文压缩和「空闲时压缩」。
- 和它配合的共识层见 [需求-记忆库](需求-记忆库.md)。
- **要先实测**：各 AI 报的用量能读到哪些（上下文长度、缓存命中、账号额度、重置时间）。

## 现在的做法

- 聊天里的 Claude Code、Codex 每一轮都是一次性会话，每轮重新发聊天记录：从最新往前装满 6 万字，超出时起点按 10 条一档往后挪；较早的、超过 8000 字的长回复只留头尾（[prompts.mjs](../src/prompts.mjs)）。挪出去的部分直接丢掉。
- 导入的对话作为固定背景每轮都带，不算进那 6 万字；API 成员另外附带最多 6 万字的文件内容。
- 任务空间的工作者每次也是一次性会话。
- 接续导入对话的 Claude Code、DeepSeek Harness 成员的会话会越来越长。

## 一、先记录用量（已完成，2026-11-19）

- 每一轮记下实际用了多少 token、缓存命中多少，按成员、按空间存。
- 后面每一条优化都拿它做依据；成员标签和上下文面板也用这份数据。
- 实测会用你的 Claude Code / Codex 账号各跑几次（2026-11-19 同意），只发编造的短消息。

### 模块与接口（2026-11-19，已按此实现）

这一步只记录，不加界面、不加后端路由（读用量的接口等接界面时再加），也不改 `chat.mjs`、`taskrun.mjs`。

| 模块 | 做什么 | 对外接口 |
| --- | --- | --- |
| 各引擎（`src/engines/*`） | 从各自的输出里读用量 | `runTurn` 的返回值多一个可选的 `usage`：`{ input, output, cacheRead, cacheWrite, contextUsed?, contextWindow?, quota?: { usedPct, resetsAt } }`，拿不到的字段不写。`meta.usage` 写这个引擎能报哪几样：`{ tokens, context, quota }`（实测后填） |
| `src/turn-runner.mjs` | 把用量记到这次调用的记录上 | `sink.usage = r.usage`。sink 本来就是聊天消息、子任务的某次派活、整理导入的记录，随空间一起保存，不另开存储 |
| `src/usage.mjs`（新） | 从空间数据里汇总，纯函数 | `summarize(spaceData, { since? }) → { [memberId]: { input, output, cacheRead, cacheWrite, turns } }`；`latest(spaceData, memberId) → usage \| null`（成员标签用最近一次的上下文和额度） |

- 实测清单：Claude Code、Codex、DeepSeek Harness 各跑一次，记下输出里有哪些用量字段；Gemini CLI 本机没装、Gemini API 和 OpenAI 兼容接口没有 key，只按官方文档写解析，标「未实测」。
- 测试：模拟引擎带上编造的用量，验证会记到消息和派活记录上、汇总对得上、缺字段时不报错。

### 实测结果（2026-11-19，Windows）

只发了「回复 ok」这类编造的短消息。统一口径：`input` 是**没命中缓存**的输入，提示总量 = input + cacheRead + cacheWrite；`contextUsed` 是这一轮最后一次请求的提示加输出；`resetsAt` 存毫秒时间戳。

| AI | token | 缓存 | 上下文 | 账号额度 | 状态 |
| --- | --- | --- | --- | --- | --- |
| Claude Code 2.1.325 | `result.usage` 是这一轮所有请求的合计（`input_tokens` 不含缓存） | `cache_read_input_tokens`、`cache_creation_input_tokens` | `result.usage.iterations` 最后一项算长度；`result.modelUsage[型号].contextWindow` 是窗口（Haiku 4.5 报 200000） | `rate_limit_event.rate_limit_info.unifiedWindows` 里 `five_hour`、`seven_day` 各有 `utilization`（0–1）和 `resetsAt`（秒）；取用得最多的一个 | 实测，三项都有 |
| Codex 0.169（`codex exec --json`，平时发言用） | `turn.completed.usage`：`input_tokens`（**含**缓存命中）、`output_tokens`、`reasoning_output_tokens` | `cached_input_tokens`、`cache_write_input_tokens` | 没有 | 没有 | 实测，只有 token |
| Codex 0.169（`app-server`，「可运行命令」且先问你时用） | `thread/tokenUsage/updated` 的 `total`（每轮一个新会话，就是这一轮） | 同上，驼峰命名 | `last`（最后一次请求）算长度，`modelContextWindow` 是窗口（报 475000） | `account/rateLimits/updated` 的 `primary` / `secondary`：`usedPercent`、`resetsAt`（秒）、`windowDurationMins`（这个账号只有一个 7 天窗口） | 实测，三项都有 |
| DeepSeek Harness | 每一步结束的 `status` / `step_end` 事件带 `usage`：`inputTokens`（不含缓存）、`outputTokens`、`totalTokens?`、`reasoningTokens?`；按步相加 | `cacheReadTokens?`、`cacheWriteTokens?`（为 0 时不出现） | 只有最后一步的长度，不报窗口 | 没有 | **未实测**：本机账号余额不足，请求被拒；按它安装包里 `dsh-headless` 的源码写 |
| Gemini CLI | `result` 事件的 `stats`：`input_tokens`（含缓存）、`output_tokens`、`input`（不含缓存） | `cached` | 没有 | 没有 | **未实测**（本机没装），按官方文档 |
| Gemini API | 最后一个分片的 `usageMetadata`：`promptTokenCount`（含缓存）+ `toolUsePromptTokenCount`，输出 = `candidatesTokenCount` + `thoughtsTokenCount` | `cachedContentTokenCount` | 提示加输出；窗口取型号列表里本来就有的 `inputTokenLimit` | 没有 | **未实测**（没有 key），按官方文档 |
| OpenAI 兼容接口 | 请求带 `stream_options: { include_usage: true }`，最后一个分片的 `usage`：`prompt_tokens`（含缓存）、`completion_tokens` | `prompt_tokens_details.cached_tokens`，DeepSeek 是 `prompt_cache_hit_tokens` | 只有长度，窗口等「预算跟着模型走」 | 没有 | **未实测**（没有 key），按 OpenAI / DeepSeek 文档 |

- Claude Code 的额度只在 `rate_limit_event` 里，`utilization` 有时只给其中一个窗口；两次实测分别读到 5 小时 92–94%、7 天 72–77%。
- Codex 的平时发言走 `codex exec`，读不到上下文和额度。要拿到就得都改走 `app-server`（「可运行命令」档已经在用它），留给后面的「成员标签」和「自动交接」决定。
- `get_context_usage`（第十一节）这次没测，等做会话型成员时再测。

### 实现情况（2026-11-19）

- 各引擎的 `runTurn` 返回可选的 `usage`，整理成统一格式的小工具在 `src/engines/usage-fields.mjs`；各引擎 `meta.usage = { tokens, context, quota }`：Claude Code、Codex、模拟引擎三项都是 true（Codex 的上下文和额度只有走 app-server 时才有）；Gemini API `context` 为 true；DeepSeek Harness、Gemini CLI、OpenAI 兼容接口只有 `tokens`。`context` 指能算出百分比（同时有长度和窗口）。
- OpenAI 兼容接口：报错里提到 `stream_options` 时去掉这个参数重发一次，并按接口地址记住，之后不再带；别的 4xx 照旧交给「不支持图片就退回纯文字」的逻辑。
- `src/turn-runner.mjs`：引擎返回 `usage` 时写 `sink.usage`。**和原接口的偏差**：同时在 sink 没有 `memberId` 时补上 `memberId`。子任务的派活记录本来不记是谁做的，只能用子任务当前的负责人推断，改派之后旧记录会算错人；旧数据仍按负责人兜底。
- `src/usage.mjs`：`records(spaceData)`、`summarize(spaceData, { since? })`、`latest(spaceData, memberId)`。遍历聊天消息（含任务空间里协调者的回复）、任务的规划消息、每次派活记录、总结；总结没有时间和成员，用任务的 `finishedAt` 和协调者兜底。给了 `since` 时，没有时间的记录不算。
- 没有记下的：整理导入（`imports.mjs`）、空间里提炼任务目标（`space.mjs`）、起草提交说明这几处的 sink 是临时对象，不随空间保存，所以用量也不保存（这一步不改这些文件）。中途出错或被中止的一轮拿不到用量，也不记。
- 测试：`test/engine-usage.test.mjs`（用实测输出的字段做样本，验证各引擎的解析；OpenAI 兼容接口的请求参数和被拒后重发），`test/usage.test.mjs`（模拟 AI 跑聊天和完整任务，用量记到消息、规划消息、派活记录、总结上，汇总对得上；缺字段、旧数据、改派、`since`、`latest`）。`npm run verify` 通过（104 项）。
- 用改好的引擎模块真实各跑了一次：Claude Code（Haiku 4.5）返回 token、上下文 8963 / 200000、额度 77%；Codex exec 只有 token；Codex app-server 返回上下文 16907 / 475000、额度 34%。只在 Windows 上验证过。

## 二、前情提要

- 聊天记录的起点每往后挪一档，就把挪出去的那部分压成摘要，追加到前情提要里，放在聊天记录前面。只在挪档时变，平时不变，不影响缓存。
- 由记忆库指定的那个成员来写（默认第一个，空间设置里能换），和整理记忆库一起做。
- **在空闲时写**：一轮结束后趁空档写好，不耽误下一轮；还没写好时这一轮先照旧显示「更早的 N 条已省略」。
- 聊天记录里在被省略的位置显示成一个折叠块，你能看也能改，改过的以你的为准，之后新增的内容接在后面。后台正在写的那次先检查版本，不覆盖你的修改。
- **能按编号找回原文**：摘要里提到的事带上消息编号，成员要细节时按编号取回原话（聊天原话按编号存成文件，见记忆库第四节）；没有读文件工具的成员，由 Agenda 把对应原文附到下一轮。
- 每次整理记下覆盖到哪条消息，以及整理自己用了多少 token。这条记录要随空间保存，不能像第一节说的整理导入那样丢掉。
- 前情提要写过程，记忆库写结论；两者同一个成员同时整理。

## 三、预算跟着模型走

- **按 token 估算**：中文一字算一个，英文四个字母算一个，不引入分词库。
- 常见模型在预设里写好上下文大小，自定义接口可以填。
- 遇到「上下文超长」的报错，自动缩小预算重试一次，并记住这个接口的大小。

## 四、总预算

- 导入的背景、聊天记录、附带的文件、记忆库加起来算一个总预算。
- 超出时：先把较早的导入改成摘要；还不够再缩聊天记录，被缩掉的部分由前情提要补上；附带的文件最后缩。

## 五、自动交接

会话会越来越长的成员，上下文用到一定比例时自动换一个新会话，就像你在 Claude Code 里换一个对话框；你只会看到它的上下文又从低处开始。

- **设置**：全局一项「上下文用到 __% 时自动交接」，默认 **50%**，可以选「不自动交接」。不做到每个成员单独设。
- **适用的成员**：单人聊天的成员、接续导入对话的 Claude Code、DeepSeek Harness、pi 成员，以及以后延续会话的成员；任务空间里正在做子任务的工作者。聊天里一次性发言的成员不需要（靠前情提要和记忆库）。
- **交接说明由旧会话自己写**：它知道得最多。在它说完一轮、你还没回的空档写，缓存还热，又便宜又不耽误下一轮。
- **新会话拿到**：记忆库里和它有关的部分；它自己的交接说明；最近几轮原文。
- **交接说明**：只写接手者从代码、记忆库和最近几轮原文里读不出来的东西，越短越好，没有就不写。通常是：试过但走不通的做法（结论能从代码里读出来，排除过的方向没处可查）；还有什么没收尾；下一步要看的原始记录编号，例如「报错见 T2 第 3 次执行」。
- 交接说明里值得全员知道的内容，交给记忆库整理进共识层，走不通的做法记成「否决过」；已经整理进记忆库的内容不在交接说明里重复。
- **正在干活的工作者不中途换**：只在说完一轮、或做完一次子任务时换。子任务中途涨满时交给 Claude Code 等自己的压缩；协调者规划时把子任务拆得够小，一个会话做得完（规划提示里加这一条）。
- **痕迹**：聊天里不显示；右侧栏的上下文面板里留一行，例如「12:30 换了新会话」。
- 拿不到用量数字的成员不做自动交接。交接说明写失败时保留旧会话，下次再试。

## 六、任务空间

- **随机标记挪到固定内容之后**：现在每次调用换一个新标记，并且放在输入第一行（[task-prompts.mjs](../src/task-prompts.mjs)），重做、打回时缓存完全用不上。改成目标、计划这些不含消息框的部分在前，标记规则紧跟在第一个消息框之前，防伪造的效果不变。
- **前置任务的报告加长度上限**，超出时只放摘要和编号，原文按需去读。
- **前置任务打回重做过时**，默认只给最新验收通过的那版，旧版标明已被取代（工作者取材料的顺序见记忆库第三节）。
- 每个成员看到的内容不同，上下文和用量按成员分开算、分开显示。
- **待定**：你针对某个子任务说的话（diff 上的批注、对它提问的回答）是否直接交给负责人、不经过协调者（参考 super-agent 的「直接投递」）。

## 七、动作摘要

- 聊天记录里每个 AI 的发言后面附一行它运行过的命令，最多几条，例如「运行了：npm test」。改了哪些文件现在已经有，不重复。

## 八、延续会话（先量再定）

- 一次性会话的好处：每个 AI 看到什么由 Agenda 说了算、各种 AI 一视同仁、设置随时生效、不弄乱你的 AI 软件历史、没有状态不会坏。代价：每轮重新读文件、重新了解项目，忘掉上一轮读过的代码和测试结果。
- 延续会话的成员历史里会留着已被取代的条目，靠记忆库追加的更正（见记忆库第三节）知道它作废了。
- 有了记忆库（防止各成员记忆分叉）和自动交接（防止会话无限变大），可以考虑折中做法：讨论进行中保持会话、只发新消息；停了一段时间（比如 10 分钟）、改了设定 / 权限 / 成员、上一轮出错或被打断、到了自动交接的比例时，换回全新会话。长会话只放在 Agenda 自己的地方，不出现在你的 Claude Code 历史里（要实测能不能做到）。
- 等第一条的用量数据出来，对比两种做法差多少再决定。
- **单人聊天不等**：只有一个成员时不存在记忆分叉的问题，直接用长会话（2026-11-19 定，见 [需求-单人聊天](需求-单人聊天.md)）。

## 九、成员标签

- 一个小圈：上下文用了多少，快满时变色；自动交接后降回低处。
- 额度快用完时标签变色提醒，平时不显示。
- 鼠标停上去一次显示「上下文 X%、额度 Y%，几点重置」。
- 一次性发言的成员不显示百分比，显示「最近 N 条在、更早的 M 条已压进前情提要」。

## 十、右侧栏「上下文」面板

- 选一个成员，列出它这次看到的内容和大概各占多少：
  - 角色说明 / 设定
  - 记忆库（带了哪几条）：每轮记下实际送进去的条目编号，事后能查「它那一轮收到的是哪条决定」，分清是整理时漏记、检索时取错，还是收到了没照做
  - 前情提要、简报、导入摘要
  - 最近 N 条聊天
  - 被省略的部分（省略了多少条、多少字）
- 自动交接的记录。
- 一个按钮「重开这个 AI 的会话」，重开时带上交接说明。正在发言时不能点。

## 十一、各 AI 显示什么

| AI | 上下文 | 额度 |
| --- | --- | --- |
| Claude Code | 读它输出里的用量；会话型成员直接问它自己（`get_context_usage`，2.1.325 起支持，不调用模型、不花额度，要实测） | 能读到就显示「已用 X%，几点重置」 |
| Codex | 读它输出里的用量 | 同上 |
| pi 成员、Claude Code 配别家模型（见 [需求-模型来源](需求-模型来源.md)） | 读 pi / Claude Code 报的用量 | 没有额度的说法，**只显示 token 数**（这个空间、今天各用了多少），不算钱，不显示接口余额 |
| 其他 | 拿不到准确数字时，只列出 Agenda 发了哪些内容，不显示百分比 | 不显示 |

## 完成标准

- `npm run verify` 通过，用模拟 AI 测试：面板里的内容拆分和送进去的条目编号、前情提要的挪档和固定前缀、你改前情提要时后台不覆盖、按编号取回原文、预算估算和超长重试、总预算的缩减顺序、自动交接的触发和交接内容、任务提示里标记的位置。
- Claude Code 和 Codex 用真实账号核对用量数字和各自显示的一致；用真实 AI 跑一次自动交接，新会话能接着做，并且不重试交接说明里写了走不通的做法。
