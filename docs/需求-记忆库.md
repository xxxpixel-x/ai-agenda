# 需求：空间记忆库

- 整理：2026-11-19；更新：2026-11-20，和 Codex 讨论后加入决定的来源和原因、「否决过」、取代用追加的更正、按任务依赖取材料
- 起因：一个空间要能一直用下去（见 [需求说明](需求说明.md) 的「产品重点」），几个 AI 来自不同厂家、每轮可能都是新会话，需要一份所有成员共用的「现在什么是对的」。参考了 [DeepSeek super-agent](https://github.com/deepseek-ai/dsh-superagent-prototype) 的「上下文当缓存」「顺着编号回忆」，[OpenMausBot](https://github.com/milind-soni/OpenMausBot) 的记忆和群聊记忆规则；Obsidian 的双向链接只作为启发。
- 定位：聊天记录是过程，记忆库是结论，是这个空间的**共识层**。
- **为 AI 设计，不为人浏览**：格式、粒度、加载方式都按 AI 好理解、好检索来定。给人看的展示前端（「记忆库」按钮，做得好看一些）放到以后，只读出来展示，不反过来影响存储格式。
- 和它配合的上下文管理（前情提要、预算、自动交接）见 [需求-上下文与额度](需求-上下文与额度.md)。

## 一、条目

一条只说一件事，单独拿出来也看得懂。

| 类型 | 例子 |
| --- | --- |
| 决定 | 登录用短信验证码 |
| 约束 | 不能引入新的依赖 |
| 项目事实 | 前端用的是 Vue 3 |
| 你的偏好 | 回复用中文；文档不要加多余的说明 |
| 未解决的问题 / 提议 | 要不要支持第三方登录（Alice 提议，还没定）；代码现在用邮箱登录，和 #12 不一致（分歧） |
| 否决过 | 登录不用邮箱：目标用户多数没有邮箱（讨论时否决）；某个库在 Windows 上跑不起来（T2 试过） |
| 任务结果 | T3 登录页做完，改了 `src/login.js` |

每条记下：

- **编号**：空间内递增，不复用，例如 `#12`。编号就是版本：同一件事有了新说法就是一条新条目，旧的标成被取代，不另加版本号；
- **类型、内容**（短，一两句）；
- **原因**：决定、约束、否决过要写，一句话说为什么。之后判断新说法能不能取代它，就看有没有回应这个原因；
- **来源**：决定才有，「你定的」或「默认通过的」（见第二节）；
- **状态**：有效 / 已被 #N 取代 / 已解决；
- **出处**：来自哪几条消息、哪个任务（哪次执行）、哪个文件，**必填**；
- **相关条目**：编号列表，例如这条决定落实在哪个任务结果里；
- **涉及的文件和主题**：用来按成员挑选；
- **日期**：原消息的时间；补导的旧对话另记导入时间。

## 二、写入规则

- **出处必填**：没有出处的不收，免得 AI 凭空「记住」不存在的事。
- **分清是谁说的**：
  - 你说的、你同意过的，记成决定（或约束、偏好），来源是「你定的」；
  - AI 提出、没人反对、并且已经照着做了的，也算决定（宽松，让你少做决定），来源是「默认通过的」，出处要指向实际照做的任务或改动；
  - 其余 AI 的建议记成「提议」，AI 没验证过的说法不算项目事实。
- **什么能取代旧条目**：同一件事、适用范围相同，并且回应了旧条目的原因，才算取代。旧条目标成「已被 #N 取代」。先后按原消息的时间算，补导的旧对话不会因为导入得晚就盖过后来的决定。
  - 「默认通过的」决定：另一个 AI 按同样的宽松规则就能改；
  - 「你定的」决定：只有你能改。AI 的做法和它不一样时，这条决定不动，另记一条项目事实（代码现在什么样）和一条分歧，整理者问你一句；
  - 分不清时也问你一句。
- **否决过**：你否掉的提议、成员实际试过走不通的做法，都记成「否决过」，写上原因，出处写明来自哪段讨论或哪个任务的哪次执行。免得别的成员换个说法再提一遍、再踩一遍。
- **任务打回重做**：新的结果记成新条目，取代旧的；旧的留着追溯。
- **谁写、什么时候写**：你在空间设置里指定的那个成员（默认第一个，可以挑便宜的），在空闲时把新的聊天、任务结果整理进来。它同时写前情提要。其他成员想记什么，在发言里说「这条记一下」，由它整理进去；其他成员不直接改记忆库。

## 三、怎么给 AI

- **只给有效的**：被取代、已解决的条目默认不加载，需要时 AI 自己去查。
- **分层加载**：
  1. 每轮都带：有效的决定、约束、你的偏好、否决过（短）；
  2. 只带目录：主题、任务，每个一行；
  3. 需要时再读：详细内容、条目的来龙去脉、聊天原话。
  超出这个成员的预算时，第 1 层也按相关程度挑。
- **按成员取**：真相只有一份，每人拿自己需要的部分。
  - 群聊：按当前话题挑。
  - 任务空间：协调者拿全局。工作者按这个顺序：全员都要遵守的约束、偏好和否决过 → 自己的子任务 → 直接依赖的前置任务最新验收通过的结果 → 按涉及的文件、主题补充。例如 T1 第一版接口被打回、第二版通过，依赖它的 T3 默认拿第二版，第一版能顺着编号查到为什么被否。
- **自动检索**：每轮发言前，Agenda 拿最新的消息去记忆库里搜相关条目，附在这一轮的输入里（放在消息里，不放系统提示，免得系统提示每轮都变）。没想到去查、或者没有读文件工具的成员也用得上。
- **顺着编号回忆**：给出的每条都带出处和相关条目的编号，AI 想深入就顺着编号去读。
- **固定格式和顺序**：按编号排列、只追加，每轮输入的前面部分不变，能命中缓存。
- **取代用追加的更正**：条目被取代时，已经发出去的内容不改，在后面追加一行，例如「#20 取代 #12：登录改回短信」。第 1 层只在前情提要挪档时重新整理一次，那时才去掉被取代的条目。这样缓存不受影响；延续会话的成员历史里还留着旧条目，也能从更正知道它作废了。

## 四、存储

- 源数据存成一行一条的结构化记录；给 AI 的是渲染好的文字，每条一行，例如：
  `#12 [决定·你定的] 登录用短信验证码——目标用户多数没有邮箱（出处：消息 128、任务 T3；相关：#7、#15）`
- 同时渲染一份文件给有读文件工具的 AI 按需查阅，聊天原话也按编号存成文件。
- 放在 Agenda 的数据目录（2026-11-20 定）：`data/spaces/<空间 ID>/memory/`，不往你的项目里放东西。交给成员时以只读方式开放这个目录，Git 副本里的工作者也读得到。
- **消息编号**：每条消息一个空间内递增、不复用的编号（`seq`），旧空间打开时按顺序补上。界面上只在鼠标停在消息时间上时显示（2026-11-20 定），记忆库和前情提要写「消息 128」时你能对得上。

## 五、展示前端（以后做）

- **是什么**：一个「记忆库」按钮，点开是这个空间记忆库的展示页，做得好看、吸引人，可以用上粒子效果（见 [需求-前端规划](需求-前端规划.md) 第七节）。
- **为什么值得做**：让你一眼看到「AI 现在记住了什么」，出了问题时方便查，有助于建立信任；也是产品的一个亮点。
- **只读出来展示**：记忆库本身还是按 AI 好理解的方式存，展示页只负责读出来，不反过来影响存储格式。
- **什么时候做**：等记忆库本身跑通了再做，不然展示的是空架子。
- **待定**：按钮放在哪（侧栏、资源库里，还是右侧栏的一个面板）；能不能在展示页里改或删条目。

## 六、模块与接口（第二批，2026-11-20，已按此实现，偏差见下面「实现情况」）

这一批做记忆库本身：编号、存储、写入规则、整理、渲染和检索。**还不送进成员的输入**：送进去要改 `prompts.mjs` 和 `chat.mjs`，单人聊天那部分也在改这两个文件，等它合并后和上下文管理（第三批）一起接。

| 模块 | 做什么 | 对外接口 |
| --- | --- | --- |
| `src/space.mjs` | 消息编号：消息发出时补 `seq`（在空间发事件的地方统一补，不改 `chat.mjs`）；打开旧空间时按顺序补上 | `message.seq`；`space.data.nextSeq` |
| `src/memory/store.mjs`（新） | 一行一条的结构化记录（`entries.jsonl`），只追加；渲染给 AI 的文字和文件（`memory.md`）；聊天原话按编号存成文件 | `openMemory(dir)` → `{ entries(), append(ops), render({ layer, member, task? }), corrections(sinceId), search(text, { limit }), lastSeq }` |
| `src/memory/rules.mjs`（新） | 写入规则：出处必填、来源（你定的 / 默认通过的）、什么能取代、你定的只有你能改（另记分歧）、否决过、补导按原时间、打回重做的新结果取代旧的 | `check(op, entries) → { ok, op?, reason? }`，纯函数 |
| `src/memory/organize.mjs`（新） | 空闲时由指定成员把新消息、任务结果整理成操作（新增 / 取代 / 解决 / 否决 / 分歧），过一遍规则再写入 | `organize(host, memory, { writer, since })`；只通过宿主接口读消息和任务结果 |
| `src/space.mjs`（接线） | 一轮结束、子任务通过后，空闲时触发整理；整理成员默认第一个成员 | `space.data.memoryWriterId`；在空间自己的事件上触发，不改 `chat.mjs`、`taskrun.mjs` |
| `src/app-server.mjs`（只加一个路由） | 只读查看，给以后的展示页和排查用 | `GET /api/spaces/:id/memory` |

- 检索不引入分词库和向量库：按字词重叠打分，中文按两个字一组切。
- 整理时自己用的 token 记下来，随空间保存。
- 测试（模拟 AI）：出处必填、来源、取代的条件、你定的只有你能改、否决过、补导按原时间、打回重做、追加更正、分层渲染、按成员和任务依赖挑选、检索、格式稳定、旧空间补编号。

### 实现情况（2026-11-20，第二批）

**还没送进成员的输入**：记忆库在后台整理、渲染和检索都能用，但聊天和任务的提示词还没带上它（要改 `prompts.mjs` / `chat.mjs` / `task-prompts.mjs`，和上下文管理一起放在第三批）。前情提要也没做，只留了接口：`compact()` 给挪档时调用。

- **消息编号**（`src/space.mjs` 的 `numberMessages`）：在 `emitEvent` 收到 `message` 事件时给这一条补，收到 `snapshot` 事件和每次 `save()` 时把还没编号的按顺序补上（导入是直接改消息列表再发 `snapshot` 的）。打开旧空间时按数组顺序补，已有的编号不动，`nextSeq` 只增不减，删掉的消息的编号也不再用。
- **存储**（`src/memory/store.mjs`）：`data/spaces/<id>/memory/` 下有 `entries.jsonl`（只追加；状态不存，由后来条目的 `supersedes` / `resolves` 和写入时的 `supersededBy` 推出来）、`state.json`（`lastSeq`、`compactedAt`）、`memory.md`（每次写入后重写：每轮都带 / 目录 / 全部条目）、`messages/<seq>.md`（原话，开头一行写编号、发言人、时间）、`organize.jsonl`（每次整理的记录）。目录在第一次写入时才建。坏行跳过。
  - 第 1 层：重整（`compact()`）之前，已经输出过的行不改，新条目接在后面，取代用 `#20 取代 #12：…` 追加更正行，所以前面的文字是后面文字的前缀（有测试）；重整之后只列当时有效的条目。
  - 工作者按四段挑选（全员遵守 → 自己的子任务 → 直接依赖最新的有效结果 → 按文件和文字相关补充，最多 8 条）；协调者和群聊拿全局。超出 `budget` 时按 `query` 的检索得分挑，输出仍按编号排。
  - 检索：英文、数字按词，汉字两个字一组，按 `log(1 + N/df)` 加权打分，默认只搜有效条目。分词在 `src/memory/tokens.mjs`。
- **写入规则**（`src/memory/rules.mjs` 的 `check`）：第二节的规则都实现了，各有测试。分不清 AI 的建议有没有被照做时，按「出处里有没有你的消息、通过的任务、带改动的 AI 消息」来判断；没有依据的决定、约束、偏好降成提议；没验证过的事实直接拒掉。补导的旧对话按原对话时间算（导入消息的 `lastTs`），比目标条目早时，写成一条已经被取代的历史条目。
- **整理**（`src/memory/organize.mjs`）：每批最多 40 条或 3 万字，积压的分批接着整理。整理成员只输出 JSON 操作，逐条过规则，拒掉的连原因记进 `organize.jsonl`。AI 失败或回的不是有效 JSON 时不推进 `lastSeq`，下次重试同一批。整理自己用的 token 记在同一条记录里。整理调用用只读权限、不续接会话。
- **接线**（`src/space.mjs`）：`createMemoryHost()`（只读：成员、`messages(since)`、`tasks()`）。触发时机：聊天的 `round_end`、任务空间里一条回复写完、`run` 事件里出现新通过的子任务。整理在后台进行，不阻塞下一轮；正在整理时又被触发就排到下一次，只多整理一次。失败只写日志，不打扰聊天。删除和退出时停掉。记忆库在空间目录里，删空间时跟着删。`space.data.memoryWriterId` 能通过 `PATCH /api/spaces/:id` 改，不给或这个成员已不在空间里时用第一个成员。
- **路由**：`GET /api/spaces/:id/memory` 返回 `{ writerId, organizing, lastSeq, compactedAt, entries, text, logs }`，只读。
- **模拟 AI**：`mock.mjs` 认出整理请求后调用 `organize.mjs` 的 `mockOps`，按编造的规则产出操作：你说「定了 / 就用」记成决定，「不要 / 否决」记成否决过，「改成」取代最新的决定，AI 说「建议」记成提议。
- 测试：`test/memory-rules.test.mjs`、`memory-store.test.mjs`、`memory-organize.test.mjs`、`memory-space.test.mjs`（共 35 项），覆盖上面列的全部情况，另加旧空间补编号、整理失败不影响聊天、整理排队、子任务通过后写结果、删空间、只读路由。`npm run verify` 通过（169 项）。

**和接口的偏差**：

- `check(op, entries, ctx?)` 多了可选的 `ctx`（消息和任务的索引）。有了它才能核实出处是否真实存在，以及分清来源。
- store 多了几个小接口：`active()`、`get(id)`、`setLastSeq(n)`、`compactedAt`、`compact()`、`archive(msgs)`、`readMessage(seq)`、`log()` / `logs()`。
- **任务结果由程序写，不交给 AI**：子任务通过后按通过的那次执行直接生成 `result` 条目，比让 AI 转述可靠。整理成员输出的 `result` 一律拒掉。打回的原因由整理成员根据提示里的打回意见记成「否决过」，程序不写。
- 有几个旧测试的假 AI 会记录调用次数，现在也会收到后台整理的调用。在 `test/helpers.mjs` 加了 `isMemoryCall` / `MEMORY_IDLE`，让这些假 AI 跳过整理调用（`clarify`、`i18n`、`import-resume`、`taskrun` 各改一行）。`settleSpace` 也会等整理停下。

**没验证 / 要注意的**：

- 只在 Windows 上用模拟 AI 跑过，**没用真实 AI 整理过**。下面这几件放到第三批：完成标准里的长讨论实测（先定 A、提议 B、确认 C、补导旧对话、交接），整理提示词在真实 AI 上的效果，以及每轮自动检索、送进输入。
- 现在每轮结束都会调一次整理成员，会花 token，但成员暂时还看不到记忆库。合并前要定一下：是先关掉，还是只在某些空间开（例如加一个开关，或者在第三批之前不触发）。打开有很多旧消息的空间时，会分批把旧消息全部整理一遍。
- 「你定的」靠出处里有没有你的消息来判断：AI 如果引用了一条无关的用户消息，规则分辨不出来。
- 记忆库目录还没以只读方式开放给成员（第三批送进输入时一起做）。展示前端以后做。

- **自动整理先关着**（2026-11-21 定）：`Space.memoryAuto` 默认 `false`，一轮结束、子任务通过时不自动整理，免得成员还看不到记忆库时白花 token；上下文管理（第三批）把记忆库送进成员输入时再打开。

## 完成标准

- `npm run verify` 通过，用模拟 AI 测试：写入规则（出处、来源、取代、否决过、补导旧对话按原时间）、分层加载、按成员挑选（含任务依赖和打回重做）、自动检索、追加更正和挪档时重整、格式稳定。
- 用真实 AI 从一段原始中文群聊开始跑，不直接往记忆库里塞条目：你先定 A，一个 AI 提议 B，你确认 C，再补导一段还在讨论 A 的旧对话，然后交接给另一个成员接着干活。检查它收到的当前决定是 C、能说出是谁定的 C、做出的改动遵循 C；A 和 B 不再被当成当前决定，B 不被重新提起。出错时按上下文面板记下的条目编号，分清是整理时记错、检索时取错，还是收到了没照做。
